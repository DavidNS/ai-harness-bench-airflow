Dags gain a ``draining`` scheduling state ("drain, then pause"): the Scheduler stops creating new runs while the runs in flight finish, and then pauses the Dag automatically. The state is exposed as ``scheduling_state`` in the REST API (``PATCH /dags`` and ``PATCH /dags/{dag_id}`` accept either ``is_paused`` or ``scheduling_state``); clients that only use ``is_paused`` are unaffected.
